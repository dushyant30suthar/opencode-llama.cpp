# vLLM + NVFP4 on sm_120 — what this box can and cannot run

Measured 2026-08-09 on prajna: 2× RTX 5060 Ti (sm_120, 16311 MiB each),
i5-9400F, 31 GB RAM, PCIe Gen3 x8/x4. vLLM 0.26.0, torch 2.11.0+cu130,
CUDA 13.3, driver 610.43.03. Everything below is from an engine startup log or
a timed request unless marked otherwise.

---

## 1. The kernel rule: the CHECKPOINT decides, not the GPU

The headline correction of this session. It is **not** true that consumer
Blackwell cannot use FP4 tensor cores. What decides is how the checkpoint was
quantised:

| checkpoint | vLLM kernel on sm_120 | evidence |
|---|---|---|
| dense, `quant_algo: NVFP4` | **`CutlassNvFp4LinearKernel`** — native FP4 | Llama-3.3-Nemotron-Super-49B-v1.5-NVFP4 |
| dense, `W4A16_NVFP4` (weight-only) | `MarlinNvFp4LinearKernel` — dequantised | nvidia/Qwen3.6-27B-NVFP4 (`MIXED_PRECISION`) |
| MoE | `'MARLIN' NvFp4 MoE backend` | nvidia/Qwen3.6-35B-A3B-NVFP4 |

Two things follow that are easy to get wrong:

**Marlin on a weight-only checkpoint is not a bug and not an sm_120 gap.** vLLM
PR #48199 states the fallback is the intended design for W4A16 on *every* GPU,
B200 included; that PR only corrects a misleading warning and changes no
behaviour. Issue #47749 reads like an SM120 defect and is not one.

**Marlin on the MoE is also not a fallback.** vLLM's own recipe for
`nvidia/Qwen3.6-35B-A3B-NVFP4` specifies `--moe-backend marlin` explicitly,
DGX Spark (GB10) included. vLLM enumerates all eight backends
(`FLASHINFER_TRTLLM`, `FLASHINFER_CUTEDSL`, `FLASHINFER_CUTLASS`,
`VLLM_CUTLASS`, `MARLIN`, …) and picks MARLIN by design. The merged SM120 NVFP4
work (#26669 Oct-2025, #29242 Nov-2025) is MoE-kernel enablement, not a
promise that MoE takes a native path here.

So: **to actually run FP4 tensor cores on these cards, want a DENSE checkpoint
whose `quant_algo` is plain `NVFP4`.** `hf_quant_config.json` is where ModelOpt
puts it when `config.json` has no `quantization_config` — check both.

## 2. The cards have 15.52 GiB usable, not 15.93

`gpu-memory-utilization` is a fraction of what the driver reports free, and that
is materially less than `nvidia-smi`'s total:

```
Free memory on device cuda:0 (15.19/15.52 GiB) on startup is less than desired
GPU memory utilization (0.98, 15.21 GiB)
```

16311 MiB = 15.93 GiB nominal → **15.52 GiB usable, 15.19 GiB free at startup.**
So 0.98 is already unreachable and ~0.96–0.97 is the practical ceiling. Every
utilization figure in the vLLM configs has less slack than it appears.

## 3. Dense KV is the binding constraint, and hybrids dodge it

Qwen3.6 is a hybrid: of 64 layers only ~16 are full attention, the rest are
gated-deltanet with fixed-size recurrent state. Only the full-attention layers
pay KV per token. A conventional dense model pays on every layer.

Measured, both at `kv-cache-dtype: fp8`:

| model | weights | KV per token | KV pool achieved |
|---|---|---|---|
| Qwen3.6-35B-A3B (MoE, hybrid) | 21.85 GiB | — | **413,484 tokens** |
| Llama-3.3-Nemotron-Super-49B (dense, 80 layers) | 28.96 GiB | **48.6 KiB** | **4,832 tokens** |

That 48.6 KiB/token is derived from the engine's own refusal: *"0.38 GiB KV
cache is needed"* for 8192 tokens.

## 4. Verdict: Llama-3.3-Nemotron-Super-49B-v1.5-NVFP4 does NOT fit

Downloaded, configured per NVIDIA's model card, and probed to failure. Kept on
disk with its config so this is not re-litigated later.

```
0.96 util, max-num-seqs 4  ->  0.07 GiB KV  ->  1,504 tokens
0.97 util, max-num-seqs 1  ->  GPU KV cache size: 4,832 tokens   <- absolute ceiling
0.98 util                  ->  refuses to start (see §2)
```

28.96 GiB of weights leaves ~2.36 GiB, and **activation memory consumed ~2.3 of
it** — KV was the leftover, not the budget. `enforce-eager` was already on
(NVIDIA uses it even on a B200), so there is no CUDA-graph memory left to
reclaim. This model wants ~40 GB.

It did prove §1: `Using CutlassNvFp4LinearKernel for NVFP4 GEMM`. The kernel
was never the problem.

## 5. Dense NVFP4 candidates, surveyed against §1 and §3

Everything checked for size, quant scheme and KV cost. **Nothing here is
measured — these are candidates, not results.**

| repo | GiB | quant | verdict |
|---|---|---|---|
| `sakamakismile/Qwen3.6-27B-Text-NVFP4-MTP` | **18.31** | modelopt **NVFP4** | best fit: hybrid (64L, `layer_types` mostly `linear_attention`), so ~32 KiB/token effective. Text-only. Name claims MTP but `num_nextn_predict_layers` is absent from config — **verify the head before trusting it** |
| `RedHatAI/gemma-4-31B-it-NVFP4` | 21.70 | compressed-tensors **W4A4** | different lab. 60L, `sliding_window: 1024` so most layers' KV is capped rather than linear; full-attention layers dominate |
| `LilaRest/gemma-4-31B-it-NVFP4-turbo` | **18.00** | modelopt **NVFP4** | same model, smaller, `Gemma4ForCausalLM` (vision stripped) |
| `unsloth/Qwen3.6-27B-NVFP4` | 21.83 | compressed-tensors W4A4/W8A8 | keeps vision; 3.7M downloads, most-trusted uploader |
| `nvidia/Qwen3.6-27B-NVFP4` | 20.43 | modelopt `MIXED_PRECISION` | **avoid for speed** — this is the W4A16 one that routes to Marlin |
| `nvidia/Gemma-4-31B-IT-NVFP4` | 30.42 | modelopt NVFP4 | too big; same trap as the 49B |

Naive "if all layers were full attention" KV, for scale: Qwen3.6-27B 128
KiB/token, gemma-4-31B 480 KiB/token. Both are overestimates — Qwen because
48/64 layers are linear attention, gemma because 1024-token sliding windows cap
most layers at a fixed cost. **Neither effective figure has been measured.**

Ruled out with data, from earlier open questions:
`poolside/Laguna-M.1` is **129.75 GiB** at NVFP4 (70 layers, 256 experts, 16
active) — not a "mid tier that fits 32 GiB"; that premise was wrong.
`Laguna-S-2.1-exl3 2.00bpw` is 28.57 GiB — same shape of failure as the 49B.

## 6. Operational traps, all cost a failed boot

**Mamba cache blocks cap `max-num-seqs`, and the error arrives late.** Qwen3.6's
gated-deltanet layers take one block per decode sequence; 132 fit here. vLLM
defaults to 256 and aborts *during CUDA graph capture*, after KV sizing has
already reported success:

```
ValueError: max_num_seqs (256) exceeds available Mamba cache blocks (132)
```

Lowering it also **grows the KV pool** — 247,164 → 299,707 tokens purely from
256 → 64, because the blocks the unused slots were holding come back as KV. On
this architecture concurrency and context trade directly, the same coupling that
pins exl3's `max_batch_size` at 4.

**CUDA 13.3 refuses gcc > 15; Fedora 44 ships 16.1.1.** FlashInfer JIT-compiles
at runtime, so engine init dies with `Ninja build failed` →
`unsupported GNU version!`. Fix: `CUDAHOSTCXX=/usr/bin/g++-15` (gcc15-c++ is
installed). Baked into `~/Projects/vllm/launch.sh`.

**NVIDIA's Llama-Nemotron tool parser is broken on vLLM 0.26.** The plugin ships
inside the checkpoint and targets `vllm==0.9.2`; 0.26 moved the modules it
imports, so it fails at load and the parser never registers:

```
ModuleNotFoundError: No module named 'vllm.entrypoints.openai.protocol'
  -> KeyError: invalid tool call parser: llama_nemotron_json
```

No built-in substitutes — the format is XML
(`<tool_call><tool>name</tool><key>value</key></tool_call>`), not the Llama-3
JSON `llama3_json` parses. Patched copy at `~/Projects/vllm/parsers/`, generator
at `~/Projects/vllm/patch_nemotron_parser.py`. The checkpoint's own file is left
untouched so a re-download cannot silently revert the fix. Mapping:

```
vllm.entrypoints.openai.protocol      -> .engine.protocol  (ToolCall, FunctionCall, Delta*)
                                      -> abstract_tool_parser re-exports the rest
vllm.entrypoints.openai.tool_parsers  -> vllm.tool_parsers
transformers_utils.tokenizer.AnyTokenizer -> vllm.tokenizers.TokenizerLike
```

**`--enable-auto-tool-choice` and `--tool-call-parser` are a pair.**
`ParserManager.get_tool_parser()` returns None unless both are set, and the
endpoint then refuses `tool_choice: "auto"`. For Qwen3.6 on vLLM the parser is
`qwen3_xml` — note exl3 uses `qwen3_coder` for the same model family; the two
engines are not interchangeable.

## 7. Where the 35B MoE landed

The model actually deployed, for reference:

```
weights 21.85 GiB | TP=2 | fp8 KV | max-num-seqs 64 | gpu-mem-util 0.955
GPU KV cache size: 413,484 tokens | 2.10x concurrency at 196,608
decode ~140 tok/s (947 tokens in 6.74 s, shallow prompt), MTP OFF
tool calls verified: finish_reason=tool_calls, arguments parsed correctly
```

Against Qwen3.6-27B EXL3 5.00bpw + MTP (75.3 t/s @4k, 58.1 @98k) that is ~1.9×,
on the Marlin path. The MoE reads ~3B active params per token against the dense
27B's ~20 GiB — that, not the kernel, is where the speed comes from.

**Not measured:** decode at depth. 140 t/s is a ~20-token prompt. The exl3
figures carry a depth curve; this one does not yet, so the two are not
comparable beyond shallow.

## 8. What to look for next

A dense checkpoint that is all three at once:
1. `quant_algo: NVFP4` (not `W4A16_NVFP4`, not `MIXED_PRECISION`) → native CUTLASS
2. ≤ ~20 GiB of weights → leaves ~9 GiB after the §2 ceiling and ~2.3 GiB of activations
3. hybrid or sliding-window attention → KV that does not scale on every layer

`sakamakismile/Qwen3.6-27B-Text-NVFP4-MTP` is the only surveyed candidate that
hits all three. It is a community upload; check the weight index for the MTP
head before trusting the name.
