# vLLM + NVFP4 on sm_120 — what this box can and cannot run

Measured 2026-08-09 on prajna: 2× RTX 5060 Ti (sm_120, 16311 MiB each),
i5-9400F, 31 GB RAM, PCIe Gen3 x8/x4. vLLM 0.26.0, torch 2.11.0+cu130,
CUDA 13.3, driver 610.43.03. Everything below is from an engine startup log or
a timed request unless marked otherwise.

---

## 1. The kernel rule: the CHECKPOINT decides, not the GPU

The headline correction of this session. It is **not** true that consumer
Blackwell cannot use FP4 tensor cores. What decides is how the checkpoint was
quantised:

| checkpoint | vLLM kernel on sm_120 | evidence |
|---|---|---|
| dense, `quant_algo: NVFP4` | **`CutlassNvFp4LinearKernel`** — native FP4 | Llama-3.3-Nemotron-Super-49B-v1.5-NVFP4 |
| dense, `W4A16_NVFP4` (weight-only) | `MarlinNvFp4LinearKernel` — dequantised | nvidia/Qwen3.6-27B-NVFP4 (`MIXED_PRECISION`) |
| MoE | `'MARLIN' NvFp4 MoE backend` | nvidia/Qwen3.6-35B-A3B-NVFP4 |

Two things follow that are easy to get wrong:

**Marlin on a weight-only checkpoint is not a bug and not an sm_120 gap.** vLLM
PR #48199 states the fallback is the intended design for W4A16 on *every* GPU,
B200 included; that PR only corrects a misleading warning and changes no
behaviour. Issue #47749 reads like an SM120 defect and is not one.

**Marlin on the MoE is also not a fallback.** vLLM's own recipe for
`nvidia/Qwen3.6-35B-A3B-NVFP4` specifies `--moe-backend marlin` explicitly,
DGX Spark (GB10) included. vLLM enumerates all eight backends
(`FLASHINFER_TRTLLM`, `FLASHINFER_CUTEDSL`, `FLASHINFER_CUTLASS`,
`VLLM_CUTLASS`, `MARLIN`, …) and picks MARLIN by design. The merged SM120 NVFP4
work (#26669 Oct-2025, #29242 Nov-2025) is MoE-kernel enablement, not a
promise that MoE takes a native path here.

So: **to actually run FP4 tensor cores on these cards, want a DENSE checkpoint
whose `quant_algo` is plain `NVFP4`.** `hf_quant_config.json` is where ModelOpt
puts it when `config.json` has no `quantization_config` — check both.

## 2. The cards have 15.52 GiB usable, not 15.93

`gpu-memory-utilization` is a fraction of what the driver reports free, and that
is materially less than `nvidia-smi`'s total:

```
Free memory on device cuda:0 (15.19/15.52 GiB) on startup is less than desired
GPU memory utilization (0.98, 15.21 GiB)
```

16311 MiB = 15.93 GiB nominal → **15.52 GiB usable, 15.19 GiB free at startup.**
So 0.98 is already unreachable and ~0.96–0.97 is the practical ceiling. Every
utilization figure in the vLLM configs has less slack than it appears.

## 3. Dense KV is the binding constraint, and hybrids dodge it

Qwen3.6 is a hybrid: of 64 layers only ~16 are full attention, the rest are
gated-deltanet with fixed-size recurrent state. Only the full-attention layers
pay KV per token. A conventional dense model pays on every layer.

Measured, both at `kv-cache-dtype: fp8`:

| model | weights | KV per token | KV pool achieved |
|---|---|---|---|
| Qwen3.6-35B-A3B (MoE, hybrid) | 21.85 GiB | — | **413,484 tokens** |
| Llama-3.3-Nemotron-Super-49B (dense, 80 layers) | 28.96 GiB | **48.6 KiB** | **4,832 tokens** |

That 48.6 KiB/token is derived from the engine's own refusal: *"0.38 GiB KV
cache is needed"* for 8192 tokens.

## 4. Verdict: Llama-3.3-Nemotron-Super-49B-v1.5-NVFP4 does NOT fit

Downloaded, configured per NVIDIA's model card, and probed to failure. Kept on
disk with its config so this is not re-litigated later.

```
0.96 util, max-num-seqs 4  ->  0.07 GiB KV  ->  1,504 tokens
0.97 util, max-num-seqs 1  ->  GPU KV cache size: 4,832 tokens   <- absolute ceiling
0.98 util                  ->  refuses to start (see §2)
```

28.96 GiB of weights leaves ~2.36 GiB, and **activation memory consumed ~2.3 of
it** — KV was the leftover, not the budget. `enforce-eager` was already on
(NVIDIA uses it even on a B200), so there is no CUDA-graph memory left to
reclaim. This model wants ~40 GB.

It did prove §1: `Using CutlassNvFp4LinearKernel for NVFP4 GEMM`. The kernel
was never the problem.

## 6. Operational traps, all cost a failed boot

**Mamba cache blocks cap `max-num-seqs`, and the error arrives late.** Qwen3.6's
gated-deltanet layers take one block per decode sequence; 132 fit here. vLLM
defaults to 256 and aborts *during CUDA graph capture*, after KV sizing has
already reported success:

```
ValueError: max_num_seqs (256) exceeds available Mamba cache blocks (132)
```

Lowering it also **grows the KV pool** — 247,164 → 299,707 tokens purely from
256 → 64, because the blocks the unused slots were holding come back as KV. On
this architecture concurrency and context trade directly, the same coupling that
pins exl3's `max_batch_size` at 4.

**CUDA 13.3 refuses gcc > 15; Fedora 44 ships 16.1.1.** FlashInfer JIT-compiles
at runtime, so engine init dies with `Ninja build failed` →
`unsupported GNU version!`. Fix: `CUDAHOSTCXX=/usr/bin/g++-15` (gcc15-c++ is
installed). Baked into `~/Projects/vllm/launch.sh`.

**NVIDIA's Llama-Nemotron tool parser is broken on vLLM 0.26.** The plugin ships
inside the checkpoint and targets `vllm==0.9.2`; 0.26 moved the modules it
imports, so it fails at load and the parser never registers:

```
ModuleNotFoundError: No module named 'vllm.entrypoints.openai.protocol'
  -> KeyError: invalid tool call parser: llama_nemotron_json
```

No built-in substitutes — the format is XML
(`<tool_call><tool>name</tool><key>value</key></tool_call>`), not the Llama-3
JSON `llama3_json` parses. Patched copy at `~/Projects/vllm/parsers/`, generator
at `~/Projects/vllm/patch_nemotron_parser.py`. The checkpoint's own file is left
untouched so a re-download cannot silently revert the fix. Mapping:

```
vllm.entrypoints.openai.protocol      -> .engine.protocol  (ToolCall, FunctionCall, Delta*)
                                      -> abstract_tool_parser re-exports the rest
vllm.entrypoints.openai.tool_parsers  -> vllm.tool_parsers
transformers_utils.tokenizer.AnyTokenizer -> vllm.tokenizers.TokenizerLike
```

**`--enable-auto-tool-choice` and `--tool-call-parser` are a pair.**
`ParserManager.get_tool_parser()` returns None unless both are set, and the
endpoint then refuses `tool_choice: "auto"`. For Qwen3.6 on vLLM the parser is
`qwen3_xml` — note exl3 uses `qwen3_coder` for the same model family; the two
engines are not interchangeable.

## 7. Where the 35B MoE landed

The model actually deployed, for reference:

```
weights 21.85 GiB | TP=2 | fp8 KV | max-num-seqs 64 | gpu-mem-util 0.955
GPU KV cache size: 413,484 tokens | 2.10x concurrency at 196,608
decode ~140 tok/s (947 tokens in 6.74 s, shallow prompt), MTP OFF
tool calls verified: finish_reason=tool_calls, arguments parsed correctly
```

Against Qwen3.6-27B EXL3 5.00bpw + MTP (75.3 t/s @4k, 58.1 @98k) that is ~1.9×,
on the Marlin path. The MoE reads ~3B active params per token against the dense
27B's ~20 GiB — that, not the kernel, is where the speed comes from.

**Not measured:** decode at depth. 140 t/s is a ~20-token prompt. The exl3
figures carry a depth curve; this one does not yet, so the two are not
comparable beyond shallow.

## 8. What to look for next

A dense checkpoint that is all three at once:
1. `quant_algo: NVFP4` (not `W4A16_NVFP4`, not `MIXED_PRECISION`) → native CUTLASS
2. ≤ ~20 GiB of weights → leaves ~9 GiB after the §2 ceiling and ~2.3 GiB of activations
3. hybrid or sliding-window attention → KV that does not scale on every layer

`sakamakismile/Qwen3.6-27B-Text-NVFP4-MTP` was named here as the only surveyed
candidate hitting all three. **That search is closed — see §9.** The NVIDIA
checkpoint already on disk has the MTP head, so there is no reason to pull a
community upload for it.

Criterion 1 also needs qualifying: `MIXED_PRECISION` is not automatically a
disqualifier. On the 27B it means FP8 attention + 4-bit MLPs, which is a
*better* checkpoint than uniform NVFP4, not a worse one. Read
`hf_quant_config.json` and see which layers got which algorithm before
judging a checkpoint by its top-level `quant_algo`.


## 9. Correction: the 27B dense is the best model on this box (measured 2026-08-09)

Three claims earlier in this document are wrong. They were written from the
checkpoint's top-level `quant_algo` and from a benchmark run with speculative
decoding switched off. Measurement overturned all three.

### 9.1 `MIXED_PRECISION` did not mean "uniformly 4-bit"

`hf_quant_config.json` lists 401 quantised layers:

| module | count | quant_algo |
|---|---|---|
| `linear_attn` | 144 | **FP8** |
| `self_attn` | 64 | **FP8** |
| `mlp` | 192 | `W4A16_NVFP4`, group 16 |
| `lm_head` | 1 | `W4A16_NVFP4` |
| KV cache | — | **FP8** |

**All 208 attention layers are 8-bit.** Only the MLPs are 4-bit. On disk the
checkpoint is 21.92 GB against 19.90 GB for turboderp's exl3 5.00bpw of the same
model — the "4-bit" build retains ~10% more bits than the "5 bpw" one.

That is also the answer to why it reads as higher quality than the exl3 build.
exl3 quantises attention harder *and* runs `cache_mode: 6,4` — 6-bit K, 4-bit V.
This build runs fp8/fp8. Attention and the KV cache are where long-range
coherence and instruction-following live.

### 9.2 The checkpoint ships an MTP head

The weight index contains `mtp.fc` + `mtp.layers.0` — 15 tensors, stored
unquantised. vLLM 0.26 registers `Qwen3_5MTP` and accepts `qwen3_5_mtp` as a
speculative method. **"NVFP4 has no MTP" was a configuration gap in this repo's
own configs, not a property of the checkpoint.**

```yaml
speculative-config:
  method: qwen3_5_mtp
  num_speculative_tokens: 3
```

### 9.3 Measured, identical prompt, temp 0, steady state

| config | decode | mean acceptance length | KV pool |
|---|---|---|---|
| no MTP | 35.0 t/s | — | 162,710 |
| k=2, batched 2048 | 63.4 | 2.66–2.76 | 134,302 |
| k=3, batched 2048 | 73.6 | 3.14–3.34 | 127,529 |
| k=4, batched 8192 | 77.7 | 3.75-3.86 | 125,551 | **OOMs at depth** |
| k=3, batched 8192 | 77.6 | 3.39-3.50 | 132,544 | **OOMs at depth** |

Two things to take from this table:

- **`max-num-batched-tokens: 8192` is a trap — do not use it.** Speculative
  decoding pins `max_num_scheduled_tokens` to 2048, and raising it to 8192 does
  take k=3 from 73.6 to 77.6. It also makes the engine OOM during *prefill* on
  prompts as small as ~7.5k tokens (`Tried to allocate 252.00 MiB ... 233.50 MiB
  is free` → `EngineDeadError`). Every row in the table above was measured on a
  ~20-token prompt, which is why none of them caught it. **Shipped config uses
  2048.**
- **k=4 is not worth it.** It ties k=3 on decode (inside run-to-run noise) but
  costs ~7,000 tokens of KV pool. Past the point where acceptance saturates,
  raising k buys nothing and spends cache.

Deployed config: k=3, `max-num-batched-tokens: 2048`, `max-model-len: 122880`,
`gpu-memory-utilization: 0.955`, `enable-prefix-caching: true`, KV pool 128,222,
reasoning on, tool calls verified. (Window is 122,880 rather than 131,072 to
make room for prefix caching — see §9.3b.)

### 9.3a Depth curve (shipped config)

Everything above is a ~20-token prompt. Streamed, temp 0, on real prompt depths:

| depth | prompt tok | TTFT | decode |
|---|---|---|---|
| 4k | 7,236 | 11.1s | 53.7 t/s (cold, first call after restart) |
| 32k | 33,941 | 46.3s | 66.5 t/s |
| 98k | 100,049 | 157.2s | 60.1 t/s |

Against exl3 5.00bpw + MTP (75.3 @4k, 58.1 @98k) this config is **ahead at 98k**.

**TTFT was the real weakness — until prefix caching.** See §9.3b. The claim
that deep prompts are simply expensive to start on this box was wrong; it was
written after testing exactly one fix (a bigger batch budget) that happened to
OOM.

### 9.3b Prefill, prefix caching, and the actual hardware ceiling

Prefix caching was **off in every measurement above**, including the depth
curve. Turning it on is the largest single improvement found:

| 100,046-token prompt | TTFT | effective prefill |
|---|---|---|
| "cold" | 114.8s | 871 t/s — **NOT a cold rate, see below** |
| **repeat** | **4.9s** | 20,321 t/s |

**The 871 t/s figure is wrong as a prefill rate.** It is
`prompt_tokens / TTFT` on a run where the preceding 32k probe had already
cached ~34k of the same prompt (both built from one generator), so it counts
cached tokens as prefilled. The clean cold number is from the depth curve in
§9.3a, taken with prefix caching off: **636 t/s**. Use that for planning.

23x, at a 55.4% cache hit rate. For coding-agent use — where each turn resends a
long shared prefix — this dominates every decode-side tuning in this document.

**Cost:** `max-model-len` must drop 131,072 → 122,880. Enabling the cache asks
for ~1% more KV than the full window leaves (2.52 GiB against 2.5 available).
KV pool 133,860 → 128,222.

**Architecture caveat.** This model is 48 `linear_attention` + 16
`full_attention` layers. The gated-deltanet layers hold a fixed-size recurrent
state rather than per-token KV, so vLLM snapshots that state at page boundaries
and forces both page types equal:

```
Mamba cache mode is set to 'align' for Qwen3_5ForConditionalGeneration
  by default when prefix caching is enabled
Padding mamba page size by 0.25% ...
Setting attention block size to 1600 tokens
Warning: Prefix caching in Mamba cache 'align' mode is ... experimental
```

Pages are **1600 tokens**, not the usual 16, so **reuse is quantised to 1600
tokens** — a turn that appends less than that re-prefills the whole trailing
page. That is why the repeat costs 4.9s and not ~0. Treat as experimental.

**This is where exl3 is better, and it is not close.** `exllamav3/constants.py`
sets `PAGE_SIZE = 256`, so exl3's cache granularity is **6.25x finer** than what
vLLM is forced into on this hybrid model. Both engines hash pages by content —
`agentic-clients-and-prefix-caching.md` establishes that llama.cpp, exllamav3
and vLLM are identical in being prefix-match caches — so the mechanism is the
same and only the page size differs. It differs in exl3's favour: recovering
from a mid-prompt divergence costs vLLM up to 1600 tokens of recompute per
affected page against exl3's 256. Given that doc's finding that client-side
prompt rewriting is the dominant real-world cost, granularity matters more than
the ~16% throughput edge below.

**Batch size is settled: use 2048.**

| batched | prefill @32k | prefill @98k | verdict |
|---|---|---|---|
| 2048 | 731 t/s | 871 t/s | shipped |
| 4096 | 732 t/s | 806 t/s | no gain, closer to the cliff |
| 8192 | — | — | OOMs during prefill |

**The real prefill ceiling is PCIe, not vLLM** — already established and
quantified in `backends-qwen27b-benchmarks.md` ("Prefill: at the hardware limit,
and 26% of it is the x4 slot"). Confirmed independently here:

```
P2P:  GPU0 <-> GPU1 = CNS  (Chipset Not Supported - no peer-to-peer)
PCIe: GPU0  Gen3 x8    GPU1  Gen3 x4
```

That earlier doc did the arithmetic properly: TP fires 128 all-reduces x 64
layers per forward, 1.31 MB in and out per rank per token, independent of chunk
size. For 98,304 tokens that is 128.8 GB each direction per rank; at GPU1's
measured 2.76 GB/s it is ~47 s, **~26% of wall time and a hard floor**. The
other ~74% is compute-bound at roughly where trellis/Marlin GEMM should land on
this card. Realistic tuning headroom is 10-20%, not 2x.

**Do not suggest reseating GPU1.** GPU1 sits on 00:1c.0, a PCH port behind DMI
3.0 on the ROG STRIX B360-F; that board does not bifurcate the CPU lanes, so
there is no CPU-attached slot to move it to. This was checked before.

### 9.4 Standing comparison

| | nvidia NVFP4 + MTP | exl3 5.00bpw + MTP |
|---|---|---|
| decode shallow | 75–76 t/s | 75.3 t/s @4k |
| decode @98k | **60.1 t/s** | 58.1 t/s |
| cold prefill @98k | **~636 t/s** | 543–553 t/s |
| cache page size | 1600 tok | **256 tok** |
| attention | **FP8** | ~5 bpw |
| KV cache | **fp8 / fp8** | 6-bit K / 4-bit V |
| window | 122,880 (prefix caching on) | 196,608 |

Same speed, higher precision, smaller window — and exl3's larger window is
bought with the lossier KV cache, so it is the same trade seen from the other
side, not a free win.

### 9.5 Unrelated correction to §1

§1 implies MoE lands on MARLIN on sm_120. That holds for
`nvidia/Qwen3.6-35B-A3B-NVFP4`, but `NVIDIA-Nemotron-3-Nano-30B-A3B-NVFP4`
selects the `VLLM_CUTLASS` NvFp4 MoE backend — **native FP4 on MoE on sm_120** —
because its `quant_algo` is pure `NVFP4`. The checkpoint's declared algorithm
decides the kernel, not the GPU.

## 10. The 35B MoE: opposite conclusions to the 27B

Same treatment applied to `nvidia/Qwen3.6-35B-A3B-NVFP4`. Two findings invert
what worked on the dense 27B.

### 10.1 MTP is useless here — do not enable it

The checkpoint ships an MoE MTP head (`mtp.fc`, `mtp.layers.0.mlp.experts.*`,
19 tensors) and vLLM registers `Qwen3_5MoeMTP`, so it runs. It just does not help:

| config | decode | acceptance |
|---|---|---|
| no MTP | 142 t/s | — |
| MTP k=3 | 143.7 / 134.0 t/s | 3.53 |

Acceptance is high and the speed does not move. MTP wins by cutting **weight
reads per token**; this MoE activates ~3B params, so there is almost nothing to
amortise and draft+verify cancels the saved passes. It also costs pool
(301,111 vs 413,484). The dense 27B gets 2.2x precisely *because* it is
memory-bound at ~20 GiB read per token. **Memory-bound → MTP; compute-bound MoE
→ no.**

### 10.2 `max-num-batched-tokens` must be >= the align page, which is 2096 here

Enabling prefix caching failed three times and looked like a memory ceiling. It
was an assertion:

```
AssertionError: In Mamba cache align mode,
  block_size (2096) must be <= max_num_batched_tokens (2048)
```

The align page is **2096 tokens on the 35B against 1600 on the 27B**, so the
2048 that is correct on the 27B is 48 tokens too small here. Use 4096 (proven at
depth; 8192 is what OOMs). **Check the reported `attention block size` before
setting this on any hybrid model** — it is model-specific.

### 10.3 Result

| | before | after |
|---|---|---|
| decode | 142 t/s | 140-141 t/s (unchanged) |
| KV pool | 413,484 | **481,689** |
| concurrency @196,608 | 1.0x | **2.45x** |
| prefix caching | off | on |
| repeat 98k prefill | — | **0.7s** |

Cutting `max-num-seqs` 64 → 8 more than paid for prefix caching's overhead —
activation memory scales with it and comes straight out of the pool. Full
196,608 window kept, depth validated at three sizes, tool calls verified.

**For subagent fan-out the 35B is the better host**: 2.45x concurrency at full
window against the 27B's 1.04x. The 27B remains the choice for single-stream
quality (FP8 attention, fp8 KV, MTP).

**Not clean:** the intermediate prefill rates measured during this run
(3431 → 5640 t/s) are contaminated by prefix-cache hits between consecutive
probes sharing a generator prefix — the same error corrected in §9.3b. Only the
0.7s repeat and the first ~3400 t/s probe are meaningful.
