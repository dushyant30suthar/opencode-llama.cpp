# Handover — 2026-08-01

exllamav3 v1.3.0, the 5.00 vs 6.00bpw question, DFlash, and a per-model config
layout for the exl3 backend.

Everything here was measured on the 2× RTX 5060 Ti box (31.86 GiB VRAM total,
i5-9400F, 31 GB RAM, PCIe Gen3 x8/x4). Predecessor: `HANDOVER-2026-07-29.md`.

---

## 1. The short version

| question | answer |
|---|---|
| Upgrade exllamav3 to v1.3.0? | **Yes, done.** 4-slot wall lifted, +14-20% decode at depth. |
| Move to 6.00bpw? | **No.** ~7% slower, ~150k less resident context, quality gain unmeasurable. |
| Use DFlash instead of MTP? | **No, but closer than first measured.** 50.5% acceptance vs MTP's 82-87%. |
| Sequential subagents still needed? | **No.** The wall that forced it is gone. |
| Run 5+ concurrent agents? | Now possible; aggregate throughput rises to ~4-5 slots. |

## 2. exllamav3 v1.3.0 — upgraded, and it matters

Built `cf05532` from `origin/dev`. Clean fast-forward: the two local fixes from
#262 are upstream, so there was nothing to rebase.

### 2.1 The 4-slot wall is LIFTED

Previously the 5th distinct conversation with MTP wedged the generator, which is
why `sequential subagents` was a standing behavioural workaround.

Test: 6 distinct conversations, ~23.4k unique tokens each (~140k total), then
revisits. Script preserved as `scratchpad/slotwall.py` in the session, method
reproduced below.

```
conv 1..6 first-touch   all OK, 34.7-46.7s each
  conv 5                OK 34.8s   <- the old wedge point
revisit conv 1,2,3      OK 0.5s each
9/9 turns completed
```

**Revisits at 0.5s against 34.7s cold — ~70×.** MTP confirmed active
("Using main model MTP component for drafting", draft modules 3/3).

Caveat on that test: the synthetic corpus is random tokens, so draft acceptance
was 0% and the accepted-token path was never exercised. Real traffic covered
that separately — a 3-subagent fan-out ran 29 requests at **86.5% mean
acceptance, 66.7% of prefill served from cache, 23 tool-call parses, no crash**.
Note main + 3 subagents = 4 conversations, still inside the old limit, so the
real run proves MTP-under-cache-hits and the synthetic run proves the wall.

Likely credit: `2c25e58` "New tree eviction strategy (oldest leaf of oldest
root), periodically drop stranded checkpoints" — it rewrites `pagetable.py`
(+312) and adds `prune_stranded()` in `cache/recurrent.py`. The commit does not
cite #260, so this is inference from the right file fixing the right symptom.

**Action: the sequential-subagent workaround can be dropped.**

### 2.2 v1.3.0 is materially faster at depth

Same model, same corpus, same harness, engine-side `Generate:` metric:

| depth | 5.00bpw on `7858de8` | 5.00bpw on v1.3.0 | delta |
|---|---|---|---|
| 4k | 74.5 | 75.3 | +1.1% |
| 32k | 62.0 | **74.3** | **+19.8%** |
| 98k | 50.8 | **58.1** | **+14.3%** |

Consistent with `04f718d`, which gates 64-bit indexing behind a constexpr to
undo an attention perf regression for tensors < 2^31 elems — it would bite
hardest where attention dominates.

Caveat: the old run's acceptance rates are unrecorded, so some of the gap could
be draft luck. A 14-20% swing over 4 reps with tight spreads is more than noise.

**Do not infer performance from commit messages.** Reading the changelog I
predicted "1-3% at most on decode" and was wrong by an order of magnitude.

### 2.3 Other commits worth knowing

- `7eca0eb` second-tier CPU cache (new `generator/cpu_cache.py`, +259) — extends
  prefix retention into host RAM. Untested here.
- `666d729` adds `EXL3_MOE_CPU_OFFLOAD` as a documented env var. Relevant to the
  Laguna-S offload question (§5.2).
- `028e5e8` fixes an int32 offset overflow in the Triton prefill kernel **at
  large geometries**, with `tests/test_triton_paged_overflow.py`. This box runs
  130-160k — correctness, not speed.
- `9f96c99` Laguna fp32 `interm_dtype` in shared expert.
- Conversion hardening: auto device ratios, `malloc_trim` + RSS feedback,
  non-finite Hessian fallback. Matters when quantizing the 35B-A3B locally.

## 3. 5.00bpw vs 6.00bpw — 5.00 stays

### 3.1 Controlled A/B

`config-5bpw-match.yml` was made byte-identical to the 6.00bpw config except
`model_name`; same corpus, harness, `cache_size 131072`, build, 4 reps after a
discarded warmup, engine `Generate:` metric.

| depth | 5.00bpw | 6.00bpw | delta | 5bpw accept | 6bpw accept |
|---|---|---|---|---|---|
| 4k | 75.3 | 69.2 | **−8.1%** | 69.0% | 65.3% |
| 32k | 74.3 | 69.7 | **−6.2%** | 80.9% | 76.9% |
| 98k | 58.1 | 53.4 | **−8.1%** | 80.8% | 74.1% |

Weights 18.53 vs 21.37 GiB (+2.84), which the cache has to give back — about
150k tokens of resident context at `cache_mode 6,4`.

**A first, uncontrolled reading showed 6.00bpw +12.4% FASTER at 32k.** That was
pure confound: it compared 6.00bpw on v1.3.0 against a 5.00bpw baseline recorded
on `7858de8`. The rule from 07-29 (trust engine metrics, not client timing) needs
a sibling: **re-baseline on the same build before believing a delta.**

Two hypotheses disproved along the way:
- "A better quant drafts better, so acceptance rises" — no, 5.00bpw drafted
  *better* (80.9% vs 76.9% @32k).
- "Decode scales with weight bytes read, so expect −15%" — actual −7%. The
  bytes-read model ignores that MTP amortises each weight read over several
  accepted tokens.

### 3.2 Quality: measured, and its limits

turboderp publishes KLD against the unquantised reference for this exact model:

| bpw | 2.00 | 3.00 | 4.00 | **5.00** | **6.00** |
|---|---|---|---|---|---|
| mean KLD | 0.639 | 0.220 | 0.080 | **0.035** | **0.013** |
| × noise floor (0.0102) | 63× | 22× | 7.8× | 3.4× | 1.3× |

For scale at the same file size: GGUF `Q4_K_M` = 0.092, AWQ `int4_g32` = 0.118.
5.00bpw is already ~2.6× closer to the reference than Q4_K_M.

**Two limits on using this to decide.** That chart is measured on
`openwebtext, 10 × 4096 tokens` — short context, where this box runs 100k+. And
aggregate KLD shows [zero correlation with composite quality among near-baseline
quants](https://byteshape.com/blogs/Evaluating-Quantized-Models/part-2/):
displacement from baseline is not direction. Separately, 4-bit quants can drop
[up to 59% on 128K retrieval](https://arxiv.org/pdf/2505.20276) while looking
fine on short context.

So: **nothing measured here says anything about 6.00bpw's output quality at
working depth.** Only its speed and its smaller cache pool. The speed cost is
certain; the fidelity gain is real but unquantified for this workload.

### 3.3 The pool-sizing trap (config error, worth recording)

The 6.00bpw config was written with `cache_size: 163840` **and**
`max_seq_len: 163840` — a pool holding exactly one maximum-length conversation.
With 3-4 agents growing to 50-68k each, they thrash:

```
4 largest contexts sum to 268,374 tokens   vs a 163,840 pool
```

Visible per-request in the 6.00bpw fan-out session:

| ctx | cached | reuse |
|---|---|---|
| 65,896 | 26,112 | 40% |
| 66,699 | 26,112 | 39% |
| 66,811 | 25,856 | 39% |
| **68,704** | **66,048** | **96%** ← uncontended, others had finished |

Same depth, 39% vs 96%, decided purely by contention. 5.00bpw runs 311,296
against a 196,608 max sequence — 1.58× headroom. **Size the pool as a multiple
of max_seq_len, not equal to it**, or cap subagents to match.

This also confounds the session-level reuse comparison (5.00bpw 66.7% vs
6.00bpw 49.8%): the 6.00bpw session did 2.5× more prefill work *and* had half
the pool. Direction is real, magnitude is not attributable.

## 4. DFlash — rejected, but the first measurement was wrong

### 4.1 What it is

`turboderp/Qwen3.6-27B-DFlash-exl3` is **not a separate base model**. Its
config.json:

```json
"architectures": ["DFlashDraftModel"],
"num_hidden_layers": 5,
"block_size": 16,
"dflash_config": { "target_layer_ids": [1, 16, 31, 46, 61] }
```

A **1.21 GiB drafter** (at 6.00bpw) that attaches to the 27B you already run,
tapping hidden states from 5 of its layers.
[Block Diffusion for Flash Speculative Decoding](https://arxiv.org/abs/2602.06036),
z-lab. Where MTP predicts tokens one at a time, DFlash generates a whole block in
one diffusion pass. It **replaces** MTP; the two are alternatives.

exllamav3 v1.3.0 supports it: `architecture/dflash.py`, and
`generator.py:255` auto-detects via `caps["dflash_draft"]`. Config is plain
`draft_mode: model` with `draft_model_name` pointing at the directory.

**It accelerates DECODE ONLY.** Prefill is already fully parallel — no
speculation possible. Prefill stayed ~525 T/s throughout.

### 4.2 `draft_num_tokens` is the whole story

The drafter runs at its fixed 16-token block, **but the generator truncates it**:

> `# The diffusion drafter always runs at its fixed block size, dynamic window truncates the drafted block` — `generator.py:653`, with `num_draft_tokens` as the ceiling (`generator.py:91`)

And that same value sets the cache's `max_history`
(`tabbyAPI/backends/exllamav3/model.py:506`), which sizes the gated-deltanet
state. Leaving it unset takes `default_draft_size = block_size - 1 = 15`
(`architecture/dflash.py:174`) — **the worst value on both axes**.

| `draft_num_tokens` | acceptance | decode median | drafted per emitted | GDN state/slot |
|---|---|---|---|---|
| unset (→15) | **15.5%** | 31.6 T/s | 4.80 | 2.39 GiB |
| **4** | **50.5%** | **42.4 T/s** | **1.17** | **0.70 GiB** |

Both runs: 6.00bpw, 1 slot, same explore prompt, reaching ~68k. Matches upstream
advice that starting at 2-4 rather than 15
["dramatically improved acceptance rates and actual throughput"](https://huggingface.co/z-lab/Qwen3.6-27B-DFlash/discussions/2).

**0.70 GiB/slot is identical to MTP's**, so at `draft_num_tokens 4` DFlash does
*not* cost concurrency — only the 1.21 GiB drafter (~63k context). The 1-slot
configs in `models/` were sized for the draft-15 state and are now unnecessarily
restrictive.

### 4.3 Why it still loses

| config | slots | decode median | acceptance | draft/token |
|---|---|---|---|---|
| 5.00bpw + MTP | 4 | 30.1 T/s | **86.7%** | 1.00 |
| 6.00bpw + MTP | 4 | 31.1 T/s | 82.0% | — |
| 6.00bpw + DFlash, draft 15 | 1 | 31.6 T/s | 15.5% | 4.80 |
| 6.00bpw + DFlash, draft 4 | 1 | **42.4 T/s** | 50.5% | 1.17 |

DFlash-at-4 has the best single-stream decode of the four — but **degrades with
depth** where MTP does not:

| ctx | DFlash acceptance | decode |
|---|---|---|
| 8,158 | 44.9% | 42.6 |
| 25,982 | 49.0% | 42.2 |
| 56,583 | 39.6% | 30.5 |
| 66,691 | **34.8%** | **26.9** |

Past ~50k it delivers 27-31 T/s — what MTP gives while serving **four concurrent
agents**. MTP holds 82-87% acceptance at every depth.

**Hypothesis for the decay:** DFlash conditions on hidden states from 5 layers of
the target. It was trained against unquantised weights; 6-bit weights shift those
activations, and the drift compounds with depth. Consistent with upstream, where
every report of DFlash working well (71.9%) is on a **BF16** target, while
[AWQ sits at 10.5-15.9%](https://huggingface.co/z-lab/Qwen3.6-27B-DFlash/discussions/2)
and a [llama.cpp issue](https://github.com/ggml-org/llama.cpp/issues/25117)
reports ~2× slowdown on a quantized MoE target. MTP's head is quantized
*alongside* the model, so it stays consistent — a structural advantage on a
quantized box.

**Untested and the one experiment left: DFlash at draft 4 with 4 slots.** Costs
the same GDN state as MTP, so it would compare drafters without also trading away
concurrency — the confound in every DFlash row above.

### 5.2 Laguna-S-2.1 — the "no EXL3 exists" blocker is gone

`turboderp/Laguna-S-2.1-exl3` published 2026-07-31, retiring the `FUTURE-PLANS.md`
ruled-out entry. Branch sizes: 2.00=28.51, 2.50=35.25, 3.00=42.12, 3.50=48.85,
4.00=55.72, 5.00=69.33 GiB.

**Only 2.00bpw fits**, and it is the worst point on its own curve — mean KLD
0.099 against a 0.0017 noise floor (58×). For contrast 3.00bpw is 0.022 and
5.00bpw 0.003.

The upside: at 28.51 GiB it would be the **first Laguna-S that runs entirely in
VRAM** — the current `UD-Q2_K_XL` GGUF is 36.96 GiB and CPU-bound. Estimated
20-30k resident context after reserve and display, extrapolating the 40 KiB/token
figure recorded for XS.

Also new 07-31: `poolside/Laguna-S-2.1-DFlash-NVFP4` / `-FP8`. The BF16 drafter
(2.08 GiB) has existed since 07-21. Note `models.ini` records DFlash as measured
**dead** for Laguna-S under llama.cpp (baseline 15.6 t/s, every draft arm
3.2-6.8) — that was a different engine and drafter, and does not transfer to the
exl3 path.

`poolside/Laguna-M.1` exists (07-14) with `-base`/`-FP8`/`-NVFP4` variants and is
absent from `FUTURE-PLANS.md` entirely — neither candidate nor rejection. A mid
tier between XS (33B-A3B) and S (117.6B) is the shape that tends to fit 32 GiB.
**Unevaluated.**

### 5.3 Qwen3.6-35B-A3B — the recommendation is now off-the-shelf

`FUTURE-PLANS.md` says quantize it locally because stock EXL3 quants used the
obsolete `mcg` codebook. For the **llama.cpp** path that is no longer needed:
`michaelw9999/Qwen3.6-35B-A3B-NVFP4-MTP-GGUF` exists — same uploader as the
deployed `michaelw9999/Qwen3.6-27B-NVFP4-MTP-GGUF` (15.08 GiB), same
NVFP4+MTP+GGUF shape. `neko-legends` published one too.

There is no official EXL3 for the 35B (`turboderp/Qwen3.6-35B-A3B-exl3` has no
bpw branches), so the EXL3 path still needs local conversion.

Note the local `lmstudio-community/Qwen3.6-35B-A3B-Q4_K_M.gguf` (19.71 GiB) is
the wrong build for this — plain Q4_K_M, no NVFP4, no MTP head.

### 5.4 EXL3 quants stop where the curve hits the noise floor

turboderp publishes down the curve and stops when KLD reaches measurement noise.
The stopping point is model-dependent: Qwen3.6-27B stops at 6.00bpw (0.013 vs a
0.0102 floor), Laguna-S-2.1 at 5.00bpw (0.003 vs 0.0017). Bigger, more redundant
models converge sooner.

EXL3 spans 1-8 bpw technically, but above ~6 the format is outside its purpose:
trellis coding wins when bits are scarce, and at 8 bits plain rounding is already
lossless while FP8 has hardware acceleration EXL3 lacks. **Third-party 8bpw
uploads exist but strip the MTP head** — `UnstableLlama/Qwen3.6-27B-exl3-8.00bpw`
has 0 `mtp.*` tensors against turboderp's 39. Losing MTP costs ~2× decode.
**Check the weight index before trusting any third-party quant.**

## 6. VRAM behaviour — three findings

### 6.1 Prefill transient is real and is NOT returned

Measured by sampling every 0.4s through a 98k prefill:

```
idle baseline        27,836 MiB
peak during prefill  30,055 MiB   (+2.14 GiB)
after completion     30,055 MiB   <- stays
```

The CUDA caching allocator keeps the block rather than returning it to the
driver. **So the "free VRAM" you see at rest only exists before the first deep
prefill.** Steady state on a working session is 30.0 GiB used, **2.5 GiB free**.

That is why `cache_size 360448` "left 53 MiB free and OOM'd everything" — it
looked fine at rest. Budget against the post-prefill steady state, not idle.

### 6.2 exllamav3 does not release VRAM on model unload

`inline_model_loading: true` was tried and reverted. It works one way:

- 5.00bpw → 6.00bpw: swapped in 34s, correct config, MTP active, 26.4 GiB
- 6.00bpw → 5.00bpw: `RuntimeError: Insufficient VRAM in split for model and
  cache`, server left with **NO model loaded and 29.2 GiB still allocated**

Only killing the process reclaims it (verified: 2/354 MiB after exit). With the
flag on, one request naming the other model takes production down until someone
restarts it.

**This validates the one-model-per-process design — the restart is what frees the
leak.** Switch models by relaunching, never in-process.

### 6.3 `tabby_config.yml` in a model folder: two traps

Per-model overrides live at `<model_dir>/<model>/tabby_config.yml` and
**always win** over the launch YAML (`common/model.py:76`).

1. **Keys must nest under `model:`.** A flat mapping is read and silently
   discarded with `"Cannot find inline model overrides"`
   (`common/model.py:98-101`). Cost: a load against the wrong `cache_size` and
   an OOM.
2. **An inline load does NOT fully inherit the launch YAML.** `max_batch_size`
   and `chunk_size` carried over; `cache_mode` fell back to the **FP16** default
   (64 KiB/token instead of 20) and `draft` came back null. VRAM 30.0 GiB
   instead of the predicted 26.0. Restate everything that matters.

**A leftover override file silently hijacks every load of that model.** One left
behind after the abandoned inline-loading experiment made a later DFlash run
actually execute MTP at 4 slots for 47 requests before it was caught.

**`draft: null` in `/v1/model` is NOT evidence MTP is off.** Native MTP uses the
head baked into the weights and never populates that field. Check the server log
for `"Using main model MTP component for drafting"`.

## 7. Concurrency — earlier claim corrected

Decode by concurrency, from the 6.00bpw fan-out session (38 requests):

| concurrent | reqs | per-agent | **aggregate** |
|---|---|---|---|
| 2 | 8 | 44.5 T/s | 88.9 |
| 3 | 6 | 32.1 | 96.3 |
| 4 | 12 | 26.5 | **106.1** |
| 5 | 10 | 21.5 | **107.4** |

**Aggregate throughput RISES with concurrency**, plateauing around 4-5.

An earlier reading of the smaller 5.00bpw session (25 requests: 76.2 solo → 60.4
at 4-way) suggested the opposite, and was used to argue that sequential agents
beat concurrent ones. That was a small-sample artifact. Concurrency buys real
aggregate throughput; per-agent latency is what it costs.

Also note **benchmark figures are single-stream.** The 6.00bpw benchmark says
69.7 T/s at 32k; the same config under a real 3-subagent fan-out has a median of
31.1. Both are correct — quote the right one.

## 8. Cache and prefix reuse — how the win actually works

Mechanism, from source:

- **Content-addressed pages.** `pagetable.py:22` — blake2b over each 256-token
  page, chained with the previous page's hash. A page's identity encodes its
  entire prefix, so two jobs sharing a prefix produce identical hashes with no
  coordination.
- **Refcounted, not copied.** N agents sharing a prefix hold one physical copy at
  `ref_count = N`; freed only when the last referrer drops it.
- **Recurrent checkpoints for the GDN layers.** State cannot be randomly
  accessed, so it is snapshotted to host RAM. v1.3.0 now drops *stranded*
  checkpoints (anchor page chain broken by KV eviction) before restorable ones.

Measured on the 5.00bpw 3-subagent session (29 requests):

```
reused from cache : 330,240 tokens
computed fresh    : 201,707
reuse rate        : 62.1%
prefill not spent : 701 s (11.7 min)
=> without the cache this session's prefill would have been 2.6x longer
```

**The split matters** — of that reuse:

| source | tokens | share |
|---|---|---|
| shared prefix across agents (3,584 × 24 requests) | 86,016 | 26% |
| each agent reusing **its own** earlier turns | 244,224 | **74%** |

So cross-agent sharing is the minority. The bulk is conversations not re-reading
their own history.

**Consequence for agent design:** the hash chain means that once two agents
diverge (different task prompts), nothing after that point can be shared *even if
they read identical files* — position is part of a page's identity. A freshly
spawned agent reuses only the common system prefix. **Continuing an existing
conversation reuses everything** (largest single hit observed: 66,048 tokens).

## 9. `opencode-localhost` — exl3 backend rework

Model selection now lives in `~/.config/opencode/providers/exl3/models/`, one
TabbyAPI YAML per model. `server.ini`'s `config` key becomes an optional
single-model override; blank means use `models/`.

Why a directory of YAMLs rather than a `models.ini` like llamacpp's: that file is
**llama.cpp's own format**, handed to `--models-preset` verbatim, and llama.cpp
routes between models itself. TabbyAPI takes one YAML naming one model, so there
is nothing to hand it and no translation worth writing.

Changes:

- **`models-dir.ts`** (new) — scans the directory, reads `model_name` and
  `max_seq_len` from each YAML without a YAML parser.
- **`models()`** now lists every YAML instead of only the loaded model.
- **`ensure(id)`** — new optional `Backend` method for engines that serve one
  model at a time. Restarts against the selected YAML; no-op when already up.
  llama.cpp's router needs no such thing and does not implement it.
- **`chat.params`** calls `ensure()` when present — the only place the plugin
  sees which model a request is for.

### Bugs found and fixed

- **id keyed on `model_name`** collapsed the dflash configs into their non-dflash
  counterparts (same served checkpoint, different settings), leaving them
  unreachable. Now keyed on the **filename**.
- **`servedModelFrom()` read `/v1/models`** — the *directory listing* — and took
  `data[0]`, i.e. whichever checkpoint sorts first, not the loaded one. Harmless
  with one model, wrong with three.
- **Status probe used `/health`**, which blocks behind TabbyAPI's generation
  queue: **10.3-16.3s under load against a 1,500ms budget**. The panel therefore
  showed "stopped / no model loaded" through an entire live session with the GPUs
  at 100%. `/v1/model` answers in 0.34s *and* names the loaded model.
- **`ensure()` restarted without waiting for the port.** `terminate()` waits for
  the parent, but under `tensor_parallel` the TP workers outlive it and keep
  holding the socket and VRAM — observed as two servers with 29.9 GiB across two
  half-loaded processes. Added `released()`, matching what `deep-confirm.sh`
  already guards against.
- **`loaded()` reported the ini's `context` and a blank `config`.** Now takes
  both from the YAML actually launched, so the panel shows the real window
  (files declare 196608 / 163840 / 131072 / 294912).
- **Display name stripped `-exl3.*$`**, collapsing `…-5.00bpw` and `…-6.00bpw`
  into an identical "Qwen3.6-27B". Now strips only the `-exl3` marker.

### Renames

`crown` was a name from an earlier session with no meaning. Gone from all live
code and config: `scripts/crown.sh` → `scripts/exl3-tp-mtp-sweep.sh` (with its
internal log names and the `exl3-TP-MTP-CROWN` label), and the tabbyAPI YAMLs it
referenced are superseded by `models/`. Historical benchmark data keeps its old
labels — rewriting recorded measurements to match a new name would falsify them.

## 10. Benchmarking rules learned today

Additions to the 07-29 rule (trust engine metrics, never client stream timing):

1. **`server.log` APPENDS across restarts.** Segment at the last
   `"Loading model:"` before analysing. Reading four runs as one produced
   "18 requests, 33.6 T/s, 55.3% acceptance" from two unrelated configs.
2. **Re-baseline on the same build.** A delta against a number from a different
   version is not a delta. This turned a real −7% into an apparent +12.4%.
3. **Verify the config actually loaded before recording anything.** Check
   `/v1/model` for `max_batch_size`, `cache_size`, and the log for which drafter.
   A leftover override file produced 47 requests of the wrong configuration.
4. **Synthetic corpora give 0% draft acceptance.** Random tokens are
   unpredictable by construction, so the accepted-token path is never exercised.
   Use `corpus.txt` or real traffic when acceptance matters.
5. **Quote single-stream and concurrent numbers separately.** They differ by
   2-3× and both are correct.
